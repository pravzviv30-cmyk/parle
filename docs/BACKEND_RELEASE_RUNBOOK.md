# Backend release and recovery

Status: portable Docker preparation; hosting is intentionally undecided. This repository does not provision a host, purchase services, push an image, apply hosted SQL, enable tutor admission, build a paid mobile release, or deploy. A passing local check is source evidence. Public launch remains blocked until the exact artifact and target have independently reviewed external acceptance.

## Artifact and service boundaries

The shared backend image runs exactly one role per container: API (`services/token-server/src/server.ts`), tutor (`services/tutor-agent/src/agent.ts start`), practice (`services/token-server/src/practiceWorker.ts`), maintenance (`services/token-server/src/maintenanceWorker.ts`), or observability (`deployment/observability.mjs`). It uses Node24.16.0, the committed npm lockfile, a required real Node base-image digest, root-owned files, and the nonroot `node` user. The runtime launcher uses `exec` so signals reach Node. Backend workspace dependency versions, including nested SDK copies, are preserved. The allowlisted Docker context excludes local environment files, keys, research, backups, learner data, tests and mobile tooling.

Node24.16.0 is an official LTS release. Docker image tags are mutable, so the base and resulting artifact must be referenced by digest. Native ORT installation downloads additional binaries; the npm lock pins package archives but does not alone prove byte-identical native installation. The image records native/model hashes. Require a Linux native-import/model test, provenance, SBOM, image scan with reviewed exceptions, and recorded image digest before promotion. Never install dependencies or download models at process startup. [Node release](https://nodejs.org/en/blog/release/v24.16.0), [Docker build guidance](https://docs.docker.com/build/building/best-practices/).

`deployment/compose.yaml` is a single-host reference. It uses only an operator-supplied immutable image and private per-role environment-file references, drops capabilities, denies new privileges, mounts a read-only root filesystem and bounded temporary storage, and requires measured CPU/memory/drain budgets. API ingress is bound to loopback; a separately reviewed TLS proxy/load balancer must expose it. No worker port is public. Compose alone supplies no HA, autoscaling, TLS certificate, network policy, alerting or database backup. Container signal grace must cover actual application drain time; its default is not a reliability proof. [Compose service reference](https://docs.docker.com/reference/compose-file/services/).

`deployment/environment-contract.json` lists names and role ownership without values. Container validation rejects known credentials belonging to another role, development shortcuts, weak callback/metrics credentials and missing secure service URLs. The tutor receives LiveKit/provider/callback credentials and never a Supabase service key. API, practice and maintenance currently use trusted `service_role`, which bypasses RLS; they do not yet have narrowly scoped independent SQL identities. Separate least-privilege SQL roles require a reviewed implementation and rollout. Keep metrics and agent callback secrets different; the read-only metrics endpoint uses `x-luvani-metrics` with `LUVANI_METRICS_SECRET`. Configure `LUVANI_TRUST_PROXY` only after proving the ingress overwrites forwarded addresses. Store secrets in the chosen host's secret manager; the portable private env-file reference is not itself a secret-management service.

Set `TTS_CACHE_DIR=/tmp/luvani-authored-cache` explicitly. The cache holds only approved authored nonpersonal lines and has application slot/entry/TTL bounds. Size the tutor temporary mount against native temporary work plus existing and pending cache files. A smaller cap safely loses cache writes but increases live synthesis cost; it is not a learner-state recovery store. Cache invalidation includes voice/model identity. Do not back up raw session audio or personal voice replies.

Maintenance and isolated restore alone receive `LUVANI_DELETION_JOURNAL_URL`, `LUVANI_DELETION_JOURNAL_TOKEN` (at least32characters) and `LUVANI_DELETION_JOURNAL_KEY` (exact32bytes,43base64url characters). Root's journal integration encrypts records with AES256GCM and uses HMAC object names; unavailable storage fails closed before external/auth erasure. This defines a transport contract, not a durable storage provider. Require independent rollback-domain isolation, conditional append/idempotent acknowledgement, readback, encryption/key recovery, retention/access controls and actual deletion replay before accepting the adapter.

## Local evidence and optional portable build

Run `node --test scripts/verifyRelease.test.mjs` and `node scripts/verifyRelease.mjs --check`. Both are offline and require the pinned root PGlite dependency. The latter replays every sorted migration into a disposable sequential fixture, checks service-only critical RPC ACLs and RLS, and inventories application schemas, roles, tables/columns/defaults, constraints, indexes, triggers, policies, functions/overloads/configuration/definition hashes, sequence privileges and default privileges. The count is dynamic; new migrations must appear automatically. Managed Auth/Storage/extension configuration and real concurrent PostgreSQL are separate acceptance, not represented by the minimal fixture.

Create a fresh catalog artifact with `node scripts/releaseSchemaManifest.mjs --output /private/tmp/release-schema.json`. Create its read-only hosted capture query with `node scripts/releaseSchemaManifest.mjs --sql /private/tmp/release-catalog.sql`. Files must not already exist. An authorized database operator executes the query using protected connection configuration, for example `PGSERVICE=<reviewed-service-name> psql --no-psqlrc --set ON_ERROR_STOP=1 --tuples-only --no-align --file /private/tmp/release-catalog.sql > /private/tmp/hosted-catalog.json`. Keep credentials out of command arguments/output. The resulting JSON is the application catalog, not the narrower `backend_catalog_v1` response. Hosted extensions or owner/default-privilege differences must be investigated, never silently ignored. If database-version formatting differs, compare against an independently replayed expected catalog on the same PostgreSQL version and review the source change; do not weaken equality to make a mismatch pass.

The dedicated `Release evidence` workflow runs source tests on pull requests/main. Its optional manual portable build requires real digest references for Node, BuildKit and the SBOM generator, builds an amd64 OCI archive, and saves provenance/SBOM metadata and a hash receipt. It performs no registry login/push or deploy. Action commits are pinned to tags verified from their official GitHub repositories on2026-10-04. It still requires a supported runner, actual container build, artifact retention/access review and exact-head successful execution. An OCI archive is not a public registry image; promotion needs the actual published digest after the registry is chosen.

For an operator-reviewed local build after committing all source, supply the verified digest through `NODE_IMAGE`, set `SOURCE_SHA` from `git rev-parse HEAD`, and run `docker buildx build --platform linux/amd64 --build-arg "NODE_IMAGE=$NODE_IMAGE" --build-arg "AUDIO_DECODER_IMAGE=$AUDIO_DECODER_IMAGE" --build-arg "AUDIO_DECODER_SHA256=$AUDIO_DECODER_SHA256" --build-arg "GIT_SHA=$SOURCE_SHA" --provenance=mode=max --attest "type=sbom,generator=$SBOM_IMAGE" --output type=oci,dest=/private/tmp/luvani-backend.oci.tar --metadata-file /private/tmp/luvani-build-metadata.json .`. The BuildKit/SBOM images must also be reviewed immutable references. No placeholder digest passes. Docker is unavailable in the current audit workspace; no container build has been claimed.

Use `production` only for production-target acceptance. This refuses a dirty/untracked source tree, a different runtime patch, mutable/fake image references, missing entrypoints or incomplete schema. It binds full HEAD SHA, lockfile hash, role source hashes, migration hashes and full catalog hash. It initially marks every external gate pending and leaves project references empty.

The candidate binds its canonical GitHub origin repository; promotion rechecks the local origin. Keep artifacts/approval records outside Git and the container context with restricted access. Approved operators must store/sign them in a protected review system; names and hashes are not authentication or a substitute for GitHub/hosting permissions.

## Migration rollout and drain

Apply reviewed migrations in filename/version order after confirming the hosted history and a usable recovery point. Use the existing Supabase migration workflow and paired rollback/runbooks; do not bulk-drop or reset production schemas. Deploy compatible readers first, then new API/maintenance/tutor/practice writers with admission OFF. Verify all new RPCs, full catalog and private exports. Old APIs cannot wrap v1 grants in legacy charge/refund primitives; old/new writers must be tested together. Configure finite owner-approved concurrency/session/issued-time budgets and provider cost safeguards. Start every required worker, observe fresh DB-server-clock heartbeats, and only then enable canary admission. The admission config's defaults remain disabled/zero.

GET `/health` is cheap process liveness. GET `/ready` uses bounded cached schema/Redis/worker checks and returns503 on missing/stale dependencies, admission OFF or draining. Readiness is required for traffic; liveness200 does not certify voice. Metrics credentials belong to operations and cannot authorize a debit. Tutor readiness proves SDK connection/registration/inference health and preflight, with physical voice and provider quality acceptance separate. Review real timings in code and test on the chosen platform.

For rolling replacement, remove the instance from new traffic, reject new jobs/admission, mark readiness false, send SIGTERM, allow bounded in-flight settlement/checkpoint and verify completion. Do not clear ledgers, reservations or receipts to speed shutdown. SIGKILL/uncertain ACK must be recovered by durable reconciliation. Maintenance acknowledges a room stop only after verified idempotent provider success; stale outbox age must alert. Restore an older compatible image only after reviewing writer/schema compatibility. Once a v1 grant has ever been issued, destructive lifecycle schema rollback is prohibited even after its account is deleted; disable admission, drain and forward-fix while preserving charge/refund/pack/job/completion evidence.

## Backup coverage and timed isolated recovery

Supabase documents daily backups for paid Pro/Team/Enterprise with plan-specific retention. PITR is a paid add-on with compute requirements and replaces daily backups when enabled. Confirm the actual project's plan, retention, accessible recovery range and latest usable point; approve RPO/RTO from measured business requirements. Do not assume backups exist on free projects. Daily downloadable backups do not contain custom role passwords, and database backups contain Storage metadata but no Storage object bodies. [Backup documentation](https://supabase.com/docs/guides/platform/backups).

A default `supabase db dump` excludes Auth/Storage/extension schemas and omits data and custom roles unless explicitly requested. It is not a complete recovery package. Managed restoration/physical clone includes database schemas/data/roles/Auth data and the encryption root key, but requires manual Storage bodies/settings, Auth/API/Realtime settings and other configuration recovery. Preserve least privileges on restore: target default privileges can otherwise widen access. Use the supported managed isolated restore flow or a separately proven complete logical procedure; do not run a generic `pg_restore --clean` against an unreviewed production/managed target. [CLI dump reference](https://supabase.com/docs/reference/cli/supabase-db-dump), [isolated project restore coverage](https://supabase.com/docs/guides/platform/clone-project).

The encrypted, access-controlled offsite inventory must cover:

- Every application schema/data and migration history, including entitlements, usage/charged/refund proof, grants, checkpoints/completion receipts, issued budgets, account fences, pack receipts/tombstones/jobs, room-stop outbox, quotas and privacy erasure workflow/history.
- Auth users and sessions; roles, effective/default privileges, RLS, functions, extensions, configuration, role-secret recovery and encryption/Vault key custody.
- Storage bucket/object metadata plus separately retained encrypted object bodies/checksums and reviewed retention/deletion handling. A metadata-only restore must fail coverage.
- Auth providers/redirects/mail/templates/API/signing configuration, Realtime settings, any functions, infrastructure/secret references, provider/LiveKit configuration, RevenueCat product/webhook mappings, Redis topology/TTL configuration and immutable server/mobile artifacts.
- A durable append-only deletion journal outside the database backup's rollback domain, with independently protected encrypted identities, high-water evidence, deletion/processor retry state and a tested replay procedure. Repository code or a configured endpoint alone does not establish storage durability.

`deployment/recoveryDrill.mjs --template /private/tmp/recovery-drill.json` creates an offline pending inventory; it performs no backup or restore. An authorized operator carries out these phases with timestamps, original evidence URLs and local hashes, then runs `node deployment/recoveryDrill.mjs --verify /private/tmp/recovery-drill.json`. The tool checks complete coverage, ordered timings, recovery targets, journal high-water continuity and exact expected/replayed deletion counts. Actual restore/check results require independent review. Measure monotonic elapsed time separately so a wall-clock correction cannot shorten the reported RTO.

1. Declare the incident/drill, pause ingress/admission, workers, scheduled jobs and outbound provider access. Select a distinct isolated target with reviewed access/network rules and start the RTO clock. Record the chosen recovery point and expected RPO.
2. Restore complete DB/Auth/roles/configuration through the supported verified procedure. Keep restored identities, queued jobs and session grants inert; restore Storage bodies/checksums separately and recover encryption/configuration/secret references under isolation.
3. Replay every deletion newer than the backup/recovery point from the independent journal before reopening API, learner authentication, queues or provider access. Repeat identity/object/processor erasure safely; verify expected deletion count and journal high water. Revoke restored sessions/rotate affected credentials under the incident policy. No deleted learner may resurrect through an old backup or queued job.
4. Compare the full app catalog and effective privileges. Run ownerA/ownerB/anon denial and Auth revocation/deletion tests, safe export, direct-write/quota checks, all critical RPC and actual concurrent PostgreSQL proofs against the isolated target.
5. Replay original/duplicate billing, charge/refund/settlement and pack/job receipts without double charges or lost baseline. Reconcile expired grants/room-stop outbox safely; prove no restored active token/job can restart unauthorised paid work. Redis limiter keys are ephemeral and must not become billing/session authority; reset only while admission is disabled and durable exposure fences remain intact.
6. Record observed RPO/RTO against approved targets, storage checksums, queue/erasure ages, failures and follow-up ownership. Independently review before reopening canary traffic. Securely delete or quarantine drill data and artifacts according to the approved retention policy; do not publish learner contents in evidence.

The current workspace has no verified hosted restore, physical-device voice/load test, real concurrent PostgreSQL acceptance, protected branch or durable external deletion-journal storage. Those remain release blockers until their evidence is captured and reviewed.

## Guest speech (founder decision D13, 5 October)

Pre-account guest speech is OFF in production until the API role sets `LUVANI_GUEST_SPEECH=1`. The switch is honoured only with `DEEPGRAM_API_KEY`, both Upstash values and the image's `LUVANI_AUDIO_DECODER_PATH`/`LUVANI_AUDIO_DECODER_SHA256`; otherwise the API logs the missing names, never their values, and guests type. `LUVANI_LOCAL_DEVELOPMENT` never opens it in production. `LUVANI_GUEST_SPEECH_DAILY_SECONDS` sets the service-wide daily ceiling of guest speech seconds (a whole number from 1 to 86,400; default 3,600; any other value keeps speech off). The other budgets are fixed in code: twenty seconds reserved per take, sixty per guest capability, sixty per installation per UTC day and three hundred per address per UTC day. They are atomic Redis counters under hashed `luvani:guest-speech:*` keys with a two-day TTL, booked before every transcription.

This budget is anonymous and sits outside the SQL paid admission in `deployment/PAID_ADMISSION.md`: it has no quote, and its spend is not part of the reviewed global exposure. Before switching it on, price the daily ceiling at the Deepgram rate and add it to the launch economics in `billingAndCost`, confirm the ingress overwrites forwarded addresses before relying on `LUVANI_TRUST_PROXY` (the address budget depends on it), and complete the security and privacy review that F735 names. The reservation and settlement Lua scripts have only been tested offline against a fake transport, so the first staging enablement must prove them on the real Redis: with a small daily ceiling, one guest's fourth take is refused, a refused take leaves the attempt unspent, the counters carry a TTL, and a take that never reaches Deepgram returns its seconds. Switching it off needs no migration or drain: unset the flag and redeploy the API; the counters expire by themselves.
