## Artifact and service boundaries

The shared backend image runs exactly one role per container: API (`services/token-server/src/server.ts`), tutor (`services/tutor-agent/src/agent.ts start`), practice (`services/token-server/src/practiceWorker.ts`), maintenance (`services/token-server/src/maintenanceWorker.ts`), or observability (`deployment/observability.mjs`). It uses Node24.16.0, the committed npm lockfile, a required real Node base-image digest, root-owned files, and the nonroot `node` user. The runtime launcher uses `exec` so signals reach Node. Backend workspace dependency versions, including nested SDK copies, are preserved. The allowlisted Docker context excludes local environment files, keys, research, backups, learner data, tests and mobile tooling.

Node24.16.0 is an official LTS release. Docker image tags are mutable, so the base and resulting artifact must be referenced by digest. Native ORT installation downloads additional binaries; the npm lock pins package archives but does not alone prove byte-identical native installation. The image records native/model hashes. Require a Linux native-import/model test, provenance, SBOM, image scan with reviewed exceptions, and recorded image digest before promotion. Never install dependencies or download models at process startup. [Node release](https://nodejs.org/en/blog/release/v24.16.0), [Docker build guidance](https://docs.docker.com/build/building/best-practices/).

`deployment/compose.yaml` is a single-host reference. It uses only an operator-supplied immutable image and private per-role environment-file references, drops capabilities, denies new privileges, mounts a read-only root filesystem and bounded temporary storage, and requires measured CPU/memory/drain budgets. API ingress is bound to loopback; a separately reviewed TLS proxy/load balancer must expose it. No worker port is public. Compose alone supplies no HA, autoscaling, TLS certificate, network policy, alerting or database backup. Container signal grace must cover actual application drain time; its default is not a reliability proof. [Compose service reference](https://docs.docker.com/reference/compose-file/services/).

`deployment/environment-contract.json` lists names and role ownership without values. Container validation rejects known credentials belonging to another role, development shortcuts, weak callback/metrics credentials and missing secure service URLs. The tutor receives LiveKit/provider/callback credentials and never a Supabase service key. API, practice and maintenance currently use trusted `service_role`, which bypasses RLS; they do not yet have narrowly scoped independent SQL identities. Separate least-privilege SQL roles require a reviewed implementation and rollout. Keep metrics and agent callback secrets different; the read-only metrics endpoint uses `x-luvani-metrics` with `LUVANI_METRICS_SECRET`. Configure `LUVANI_TRUST_PROXY` only after proving the ingress overwrites forwarded addresses. Store secrets in the chosen host's secret manager; the portable private env-file reference is not itself a secret-management service.

The production brain is OpenAI only (founder decision, 19 October 2026). API, practice and tutor require `TUTOR_LLM=openai` with `OPENAI_API_KEY`; `deployment/validateEnvironment.mjs`, the token server's `productionConfigurationProblems` (which also refuses a set `LUVANI_BRAIN` other than `openai`) and the tutor's production preflight all refuse Anthropic, Groq and the Claude CLI brains. Local development keeps every brain.

Set `TTS_CACHE_DIR=/tmp/luvani-authored-cache` explicitly. The cache holds only approved authored nonpersonal lines and has application slot/entry/TTL bounds. Size the tutor temporary mount against native temporary work plus existing and pending cache files. A smaller cap safely loses cache writes but increases live synthesis cost; it is not a learner-state recovery store. Cache invalidation includes voice/model identity. Do not back up raw session audio or personal voice replies.

Maintenance and isolated restore alone receive `LUVANI_DELETION_JOURNAL_URL`, `LUVANI_DELETION_JOURNAL_TOKEN` (at least32characters) and `LUVANI_DELETION_JOURNAL_KEY` (exact32bytes,43base64url characters). Root's journal integration encrypts records with AES256GCM and uses HMAC object names; unavailable storage fails closed before external/auth erasure. This defines a transport contract, not a durable storage provider. Require independent rollback-domain isolation, conditional append/idempotent acknowledgement, readback, encryption/key recovery, retention/access controls and actual deletion replay before accepting the adapter.

## Store free trial and yearly plans (F733, 5 October)

Founder decision D16. What the server grants, whatever App Store Connect is configured with:

- A store free trial (RevenueCat `period_type` trial on the subscriber record) is projected as the chosen plan with a week of its allowance, allowance x 7/30 (Starter 42 minutes, Max 70), until the trial ends. The first paid period after it grants the full monthly allowance. A longer trial configured in the store still grants one week.
- A yearly product grants the plan's monthly allowance one 30-day window at a time inside the paid year: twelve windows, the last running to the end of the year. The period on record (`period_end`) is the paid year, which is all a plan ever lapses from; the current window sits beside it in `allowance_window_end` and only says when the next refill is owed. A window that ends before the next one is granted leaves the learner with what the last window left them, never lapsed. `/billing/status` reports the window's end as `periodEnd`, because every screen reads that field as when the minutes start fresh.
- The part of an allowance a window does not grant is recorded as already spent, so every existing debit, reservation, refund and lapse function enforces the trial cap without change.
- A vendor answer that has already ended on the database clock (a read that crossed a window or period boundary in flight) grants nothing and takes nothing. Only the vendor saying the learner holds nothing ends a plan in the projection; otherwise only the lazy lapse a day after the paid period does.
- Store answers are ordered by when their period started (RevenueCat's `purchase_date`, kept in `entitlements.period_start`) before their end (F733 second review, 6 October). A later start is a new period whatever its end, so an upgrade Apple applies at once (Starter yearly to Max monthly ends eleven months before the year it replaces) is granted at once, and a late read of the refunded year moves nothing. With the same start, a later window refills and a later end with the same window keeps what was spent. A row with no start on record (every row from before this migration, and any period the six-argument projection wrote) is ordered by end, as before.
- The part of a window's allowance it withholds is kept in `entitlements.withheld_seconds`, so a trial read that lagged a conversion is made whole by the paid read of the same period. `seconds_used` still includes it: a learner's real usage is `seconds_used - withheld_seconds`, and session by session it is `session_usage.charged_seconds`.
- A purchase whose period type is missing or unrecognised, a yearly product with no purchase date, and any product id the server was not given are refused as unknown products (logged as `REVENUECAT_UNKNOWN_PRODUCT`). Nothing is guessed.
- A subscriber record with no entitlement under the configured `REVENUECAT_ENTITLEMENT_ID` but with another unexpired entitlement, or an unexpired subscription to a configured product, is held rather than read as holding nothing (logged as `REVENUECAT_ENTITLEMENT_MISSING`). A wrong entitlement id on the maintenance worker therefore stops refills and lapses, and never lapses a payer. A learner who also holds an unrelated live entitlement is only ever lapsed by the lazy lapse a day after their period.
- A paid introductory price (`period_type` intro) is a period somebody paid for and is granted the full allowance. None is planned; price its margin in `meter.ts` before configuring one. The app shows only a free trial as a trial.
- The subscription record is read by product id, which is how RevenueCat keys App Store products. Google Play keying is unverified; an Android purchase that does not match is refused as an unknown product, so verify it before Android sells.
- The maintenance worker's renewal sweep grants the next yearly window on time, because RevenueCat sends nothing when a month inside a year ends. Every five minutes it reads the paid rows whose period or window on record has ended (`billing_renewals_due_v1`, newest first, at most 100), re-reads at most ten subscribers from RevenueCat, and projects only what the vendor verifies through the same ticketed projection a webhook uses. The ten are the rows on the page never asked, then the rows asked longest ago, so rows stuck waiting on the store cannot starve the rest. It lapses a row only once the 24-hour slack has passed and the vendor holds nothing. It also recovers a monthly renewal whose webhook was lost. On the error stream: `billing_renewals_backlog` when a sweep reads a full page (rows past the page were not read that time), and `billing_renewals_stuck` with a count and the oldest wait in hours when any row on the page has been due for more than a day. Alert on both; a monthly lapse can show as stuck for up to about 35 minutes, and once a couple of learners cancel each hour some row is nearly always in that window, so alert when `billing_renewals_stuck` reports an oldest wait of 26 hours or more, not on persistence. `BILLING_RENEWAL_SUPERSEDED` means the store holds a plan and the projection moved nothing for a row still due: investigate it.
- Apple Billing Grace Period and Google Play's grace period should stay off for these subscriptions until a sandbox check. The server no longer depends on that switch: an answer whose `grace_period_expires_date` is a valid instant at or after its expiry is held (logged as `REVENUECAT_GRACE_PERIOD`), grants nothing new, and leaves the period on record to lapse on its own a day after it ends. A payment that lands moves the expiry a whole period on, past the grace end, and that period is granted as usual. Sandbox check before turning either on: a 7-day trial whose renewal payment fails must show the trial's week and then lapse, never a month, and RevenueCat must report the grace end in `grace_period_expires_date`.
- App Store Connect: all four products sit in the one subscription group, and both Max products (monthly and yearly) rank above both Starter products. Apple then treats Starter to Max as an upgrade, applied at once with the rest of the old plan refunded, which is what the start ordering above grants at once; Max to Starter is a downgrade that starts at the next renewal. A ranking that puts any Starter product above a Max product turns a learner's move to Max into a deferred downgrade, paid for later than they expect. Each tier's monthly and yearly products share one level, so a switch between them within a tier is a crossgrade that takes effect at the next renewal; ranking a tier's monthly above its yearly would make that switch immediate, move the period end earlier, and leave the app's pending-purchase check waiting for a plan change that never comes.

## Weekly free taste (founder decision D24, 20 October)

The one-off thirty free minutes are now a weekly free taste of five minutes (`PLANS.trial`, 300 seconds), migration `20261020140000_weekly_free_taste.sql`.

- Only a trial row with `weekly_taste` true refills: one the device claim created, or one a paid plan lapsed into. A row `begin_billing_refresh` creates without a claim is a spent taste that never refills.
- On a trial row `period_end` is when the taste refills, and `/billing/status` returns it as `periodEnd`. It is null until the first debit of a window, which sets it seven days out without starting a new usage epoch. A passed window refills on the next read or reservation (a new usage epoch); the refill waits while a claimed session is live, so that session is charged to its own window and is never stopped by the refill.
- A lapse lands on a fresh taste with `lapsed_from_paid` kept. `subscription-lapsed` is the refusal only once that taste is spent.
- The guest first scene is no longer debited from the taste at `/onboarding/claim`; its cost stays bounded by the guest speech budget.
- Deploy order: the migration, then the token server, then the app. Rollback is `supabase/rollback/20261020140000_down.sql` behind `luvani.reopen_one_off_trial`; roll back the server and app first.

## Guest speech (founder decision D13, 5 October)

Pre-account guest speech is OFF in production until the API role sets `LUVANI_GUEST_SPEECH=1`. The switch is honoured only with `DEEPGRAM_API_KEY`, both Upstash values and the image's `LUVANI_AUDIO_DECODER_PATH`/`LUVANI_AUDIO_DECODER_SHA256`; otherwise the API logs the missing names, never their values, and guests type. `LUVANI_LOCAL_DEVELOPMENT` never opens it in production. `LUVANI_GUEST_SPEECH_DAILY_SECONDS` sets the service-wide daily ceiling of guest speech seconds (a whole number from 1 to 86,400; default 3,600; any other value keeps speech off). The other budgets are fixed in code: twenty seconds reserved per take, sixty per guest capability, sixty per installation per UTC day and three hundred per address per UTC day. An IPv6 address counts by its /64, as it does for every per-address request limit; IPv4 counts by the whole address. They are atomic Redis counters under hashed `luvani:guest-speech:*` keys with a two-day TTL, booked before every transcription. A request that ends before its transcription starts returns its seconds. When the service-wide ceiling first refuses speech on a UTC day, each API process logs `guest speech: the service-wide daily budget of N s is spent` once, with no guest, installation or address in it. Guest takes hold at most one of a process's two audio decoders, so paid scoring and transcription always keep one; a guest take that finds its decoder busy sends nothing and returns its seconds.

This budget is anonymous and sits outside the SQL paid admission in `deployment/PAID_ADMISSION.md`: it has no quote, and its spend is not part of the reviewed global exposure. Before switching it on, price the daily ceiling at the Deepgram rate and add it to the launch economics in `billingAndCost`, confirm the ingress overwrites forwarded addresses before relying on `LUVANI_TRUST_PROXY` (the address budget depends on it), and complete the security and privacy review that F735 names. The reservation and settlement Lua scripts have only been tested offline against a fake transport, so the first staging enablement must prove them on the real Redis: with a small daily ceiling, one guest's fourth take is refused, a refused take leaves the attempt unspent, the counters carry a TTL, and a take that never reaches Deepgram returns its seconds. The same enablement must show that one real iOS and one real Android guest take decodes, is transcribed, and settles to its length. The decoder reads a take through a pipe, so an M4A with its index at the end is refused rather than measured, and the guest recorder uses `RecordingPresets.HIGH_QUALITY`; only a take from each real device proves the format arrives decodable. Do not set `LUVANI_GUEST_SPEECH=1` until the Phase 2 client shows the microphone only when the start reports `speechAvailable`, and turns a 503 from `/onboarding/audio` into a calm move to typing. Switching it off needs no migration or drain: unset the flag and redeploy the API; the counters expire by themselves.

## Guest first scene (UI-011, 23 October)

The guest first scene is one five-turn scripted café exchange before sign-up, with no language model ([change plan](changes/guest-first-scene.md)). It is OFF in production until both the API role and the tutor role set `LUVANI_GUEST_SCENE=1`.

- **API switch.** The API honours the switch only with both Upstash values, `LUVANI_AGENT_SECRET` and the LiveKit keys. Otherwise it logs the missing names, never their values, and the app shows the account handoff. `LUVANI_LOCAL_DEVELOPMENT` never opens it in production.
- **Tutor switch.** Without the switch, the tutor role refuses scene rooms. The guest conversation stays refused in production on both roles.
- **Budgets.**
  - **Daily ceiling.** `LUVANI_GUEST_SCENE_DAILY` is a whole number from 1 to 2,000 (default 24). Any other value keeps scenes off. It is booked atomically when the worker claims a room, so a room nobody joins spends no slot. When the ceiling first refuses on a UTC day, each API process logs `guest scene: the service-wide daily ceiling of N is spent` once, with no guest, installation or address in the line.
  - **One scene per installation per 30 days.** This is a hashed marker, a courtesy limit only: a reinstall or a forged header gets past it.
  - **Three guest starts per address per day.** An IPv6 address counts by its /64.
  - **One room per guest capability.** The capability lasts 24 hours.
- **Hard limits.** Each room lasts 180 s at most, enforced by the worker lifecycle. The guest scene gate on the paid voice proxy admits only Deepgram STT (180 s of audio in total) and ElevenLabs TTS of the scene's exact scripted lines in the signed voice. Every other effect is refused.
- **Retention.** Guest records last 30 days. A claimed record shrinks to its owner binding with a 48-hour TTL.
