# Portable monitoring and evidence toolkit

This is local implementation and capture validation. No Prometheus/Alertmanager host, alert receiver, on-call assignment, production probe, Docker build or alert delivery has been provisioned or verified. The example configuration is disabled. The six alert thresholds are provisional until operator review binds the actual deployed configuration and rules.

`observability.mjs` is a dependency-free Node exporter. It pulls exactly one pinned API instance synchronously on each `/metrics` scrape, using HTTPS `/internal/metrics`, a dedicated `LUVANI_METRICS_SECRET` from environment, no redirects, a five-second headers/body deadline and a 64-KiB source bound. It does not log URLs, credentials, upstream bodies, user IDs or arbitrary label values. Bind defaults to loopback; only loopback/private literal IPs are accepted. No open-network default exists.

Startup requires an operator-created enabled copy of `observability.example.json` with an actual direct API-instance URL. Do not point it at a load balancer that alternates processes. Supply the metrics secret separately, then run:

```sh
node deployment/observability.mjs /run/config/observability.json
```

The prepared image copies this exporter and defines a dedicated nonroot observability role with a read-only filesystem and separate secret contract. The Linux Compose reference uses host networking and enforces127.0.0.1:9464 plus the exact mounted `/run/config/observability.json`; Prometheus scrapes in that same host namespace. The image/network have not been built or deployed. The exporter needs only the metrics secret and its configuration; it needs no Supabase, LiveKit, agent or provider key. A Docker deployment using loopback bind must share the Prometheus network namespace or put the scrape on the same host; a separate container cannot reach another container's loopback. For a private network bind, choose the actual private interface and enforce network access at the selected host. Hosting remains unselected.

The source JSON contract is `{http,operations}`. `http` has exact durationBoundsMs, routes, and process `{bootId,startedAt}`. `operations` is the existing backend_status_v1 version1 tuple of tutor/practice/maintenance readiness, erasurePending and erasureOldestSeconds. Unknown fields/routes or malformed integer counts refuse collection. Observed boot changes/decreasing counters increment a content-free reset counter, while raw HTTP counters preserve Prometheus reset semantics. Boot UUIDs are never metric labels. Counters are per API process; workers/erasure values are shared DB aggregates. Aggregate worker health with `max`, and erasure gauges with `max`; do not sum the same DB snapshot across instances. Exporter restart resets its own observed-reset counter. Missing backend metrics are omitted on source failure rather than presenting a previous healthy snapshot.

The API's noncumulative duration bins become cumulative `le` bucket counters in seconds plus an observation count. There is no recorded duration sum, so the exporter does not fabricate one or advertise a complete histogram family. `histogram_quantile` may estimate p95 from those buckets; this is a bucket estimate and has no raw-timing precision. Errors cover HTTP5xx and premature closes499, not every application/business failure. Workers mean at least one recent ready heartbeat per role; they do not prove provider service availability. HTTP metrics exclude user/session/room/model labels.

The design follows Prometheus guidance on [one-instance exporters, synchronous collection, base units and cumulative buckets](https://prometheus.io/docs/instrumenting/writing_exporters/) and [histogram interpretation](https://prometheus.io/docs/practices/histograms/). Alert [grouping/routing/receiver management](https://prometheus.io/docs/alerting/latest/alertmanager/) belongs to deployed Alertmanager/operator configuration. Retrieved 2026-10-04; Firecrawl DNS was unavailable, so official pages were verified through the built-in browser research tool.

`observability.rules.yml` matches `observability.rules.json`: exporter missing, source invalid, required worker missing, old erasure, public HTTP error ratio and p95 latency. The initial one-hour erasure, one-percent errors, one-second p95 and sample-count windows are proposed thresholds, not measured SLOs. `observability.prometheus.yml` supplies local scrape wiring only; it defines no imaginary receiver or team. Actual `promtool check rules`, retention, secure Prometheus ingress, threshold approval and alert firing/delivery/acknowledgement are external acceptance.

`observabilityAcceptance.mjs` exports `validateMonitoringAcceptance(record, expected)` and `verifyMonitoringAcceptanceArtifacts(record, expected)`. Expected is `{releaseSha256,configSha256,rulesSha256}`. Exact version1 captures bind those hashes, a named API instance, assigned team, positive approved maxAckSeconds, all six alert probes and actual local hashed evidence copies. Probes require ordered fire/delivery/ack timestamps within the reviewed allowance and structured receiver delivery IDs. The configuration must be enabled/private and match the instance; the rules must contain all six alerts. A captured successful promtool result must bind the exact rules hash. Two distinct current review JSON files approve the canonical capture hash and scope `thresholds-routing-oncall`; reviews expire within seven days. Base evidence is `{url,sha256,artifactPath}` with HTTPS source links and bounded local copies. Review file digests are outside the subject identity to avoid self-referential hashes.

Pure validation always reports reviewedCaptureAccepted=false. Artifact verification can accept an `operator-capture` reviewed record after integrity checks; synthetic records never pass that acceptance. `independentlyDelivered` remains false because the validator cannot send probes or authenticate receiver history/human authors itself. Source authenticity, team assignment, review authorization and actual test delivery still require the independent promotion review. A collection endpoint and YAML file alone do not establish an operational incident response system.

Local checks: six exporter/rule tests and three monitoring-evidence tests pass, including malformed/content labels, timeout despite an uncooperative transport, bounded bodies, stale omission, cumulative bins, concurrent scrape coalescing, reset semantics, required delivery inventory and artifact tampering. No actual promtool binary or production alert receiver was used by these tests.
